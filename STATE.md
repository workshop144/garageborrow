The notifier's IAM policy now includes `dynamodb:DeleteItem` for `releaseDispatch()`.
- Auth is phone-only via Cognito custom auth. Accounts are created by invite only (no self-service SignUp, PR #14). The caller's identity is the verified phone from the ID token (PR #12). One SMS per sign-in, the code is reused across challenge retries (PR #9).

- Data export is a direct download, never emailed (PR #11). Members never see donor or voter phones (PR #3).
- `/v1/me` (sec/2026-11-06c): memberships are a member-facing projection (`garage_id, joined_at, borrows_*, returns_*, celebration_pending`); owner `notes`, `tier`, `ai_budget_override_tokens`, `vouched_by_phone` and the top-level `tier` are gone. The web uses `is_owner` and the capability list `ai_eligible_garages` (garages where the tier reaches that garage's `ai_min_tier`; Pegboard checks the current garage) instead; the "Family member" badge on My Stuff was dropped. Donor-facing donation rows (`/donations/mine`, `/v1/me/donations`, export) use `memberDonationView` (no `owner_notes`, no `decided_by_phone`; `decline_reason` stays, it is written for the donor).
- Deletion (sec/2026-11-06c): `loadGarageContext` returns 403 once a member's profile in that garage has `deleted_at`; the garage owner is exempt, so an owner who requested deletion keeps the garage page, item management, disputes and `/admin/*`. `POST /v1/me/delete-request` is a 409 while the caller has active/overdue loans or approved reservations that have not ended (read via GSI1, so eventually consistent); on success it cancels the caller's pending reservations (conditional on still pending) and removes their waitlist entries. `POST /v1/me/delete-request/cancel` clears `deleted_at` on every profile row (idempotent; 404 once the cleaner has run); withdrawn requests stay withdrawn. Members cancel their own pending/approved reservation with `DELETE /v1/g/:garage/reservations/:id` (the route My Stuff already called).
- `GET /v1/me/data-export` returns every record keyed by the phone: profiles, memberships (member view), loans and reservations (GSI1), waitlist, donations, wishlist requests and votes, notifications, push subscriptions (endpoint and created_at only). PK/SK/GSI attributes and other people's phone numbers are stripped at every depth (nested payloads too; phones quoted in text become `[redacted]`). privacy.md describes the in-app JSON download.
- Loans: last-unit commit is atomic and a closed garage blocks borrowing (PR #20).
- Loan lifecycle (fix/bugs-2026-11-06): loan rows carry a `rev` and every replace is conditional on it (`updateLoan(next, prev)`). Only the borrower can claim a return, once; an owner dispute removes the claim so the unit counts as out again, and the borrower cannot claim a disputed loan again (only the owner's return closes it). The notifier cron auto-confirms undisputed claims older than 48h (`lib/loan-lifecycle.ts`), skips reminders for claimed loans, and settles member counters on time vs late; owner returns settle counters too and accept overdue loans. Extensions go through the availability check and the item lock, max 3 per loan. `duration_days` is capped at 60.
- Approval-required borrows and reservations notify the owner (`borrow_request_pending`); the owner lists them at `GET /admin/reservations` and decides with `POST /admin/reservations/:id/decide`. The web app has no screen for this yet.
- Borrow request limits (sec/2026-11-06c, D-012, `apps/api/src/lib/borrow-limits.ts`): approval-path `POST /loans` and every `POST /reservations` count against a 20/day `borrow-request` counter keyed by garage and phone (429). The count is taken only after the window, open-request and availability checks pass, just before the row is written, so a refused request (reversed window 400, item out or garage closed 409) costs nothing; `assertReservationWindow` checks start < end first. A second pending request for the same item is a 409 while that pending request's window has not ended (a stale undecided one no longer blocks). Reservations are at most 60 days long and start at most 90 days ahead (400), and a member holds at most 2 open approved reservations per item (409). `GET /admin/reservations` pages with a keyset cursor on `(start_at, id)` (`limit` default 50, `cursor`, `next_cursor`), so deciding rows from an earlier page skips nothing; it used to return every row, no web screen calls it yet. It validates `status`. The owner cancels an approved reservation with `POST /admin/reservations/:id/cancel` (conditional on `approved`, audited, member notified); cancels by owner or borrower write `cancelled_at` / `cancelled_by_phone` and leave `decided_at` / `decided_by_phone` as the approval. `borrow_request_pending` uses its own owner notification bucket (`borrow_requests_notified_today`, 10/day), which the account cleaner resets with `notifications_sent_today`. Local checks after PR #42 review fixes: lint, typecheck clean; tests 120 shared + 276 api + 139 web = 535 passing; `pnpm -r build` ok. The open-request checks read and then write without a condition, so concurrent requests can slip past them; the atomic daily counter still bounds the total.
